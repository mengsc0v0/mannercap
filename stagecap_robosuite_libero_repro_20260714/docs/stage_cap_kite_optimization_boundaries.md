# Stage-CAP + Online KITE 方案优化边界

本文档用于交付和复现实验，明确我们现在逐步优化的逻辑、哪些改动属于方法本身、哪些改动只能用于调试、哪些改动在正式评测中不允许使用。

## 1. 我们真正要验证的方案

目标不是手写一个能完成 LIBERO 任务的 oracle policy，而是验证下面这套自动数据生成流程是否有效：

1. **阶段规划**
   将自然语言任务拆成可验证的子阶段，例如：
   - ground handle/object/target
   - sleeve or hook drawer handle
   - test drawer progress
   - pull/open/close
   - pick/lift
   - transport
   - release and verify

2. **阶段级 CAP 代码生成**
   对每个当前阶段，让 MIMO 根据：
   - stage plan
   - allowed API
   - readonly scene snapshot
   - previous stage attempts
   - online failure feedback

   生成当前阶段的 CAP 代码。

3. **阶段级验证**
   每段 CAP 执行后必须打印：

   ```text
   STAGE_STATUS {"stage_id": "...", "status": "...", "evidence": "...", "repair": "..."}
   ```

   runner 根据 `status/evidence/stderr` 决定：
   - `proceed`
   - `retry_stage`
   - `replan_stage`
   - `replan_suffix`
   - `fail_task`

4. **单轮次内失败帧监测**
   当某个阶段失败时，立即保存：
   - raw frame
   - annotated frame
   - raw evidence
   - raw repair
   - template feedback
   - scene snapshot

   后续同一阶段重新生成代码时，将失败图像和结构化反馈一起提供给 MIMO。

5. **重规划与修复**
   MIMO 不从头重做整个任务，而是根据当前阶段失败原因，修复当前阶段或后缀阶段。

## 2. 正式评测必须满足的条件

正式评测条件应当是：

```text
MIMO generates/repairs stage CAP code
Stage planner provides boundaries and verifier checks
Online KITE captures substage failure frames
Feedback is generated by fixed generic templates
No task-specific expert code is inserted
No deterministic fast-path is enabled
```

当前代码中的关键开关：

```yaml
use_stage_verifiable_runner: true
use_kite_feedback: true
use_online_stage_kite_feedback: true
use_deterministic_stage_fast_paths: false
max_total_stage_attempts: 10
```

`use_deterministic_stage_fast_paths` 在正式评测中必须为 `false`。

每个任务的阶段执行/修复总尝试次数最多为 10。这个限制是正式评测边界的一部分，避免通过无限重试把失败任务“磨”成成功。

## 3. 什么是允许的“方法优化”

允许的优化必须满足两个条件：

1. 对一类任务或一类阶段通用。
2. 不直接给出某个具体任务的完整成功轨迹代码。

### 3.1 阶段边界优化

允许改：

- drawer 任务必须先 ground handle，再 sleeve/hook，再 test progress，再 pull/open。
- pick 任务必须先 verify held/lift stability，再 transport。
- release 任务必须 verify relation predicate，而不是只看 gripper open。
- close drawer 任务必须 verify BDDL close/open diagnostics。

不允许改：

- 针对某个 task id 写“先移动到这个具体坐标，然后拉 0.42m”。
- 根据某次失败轨迹手写一条只适用于该任务的特殊阶段。

### 3.2 API contract 优化

允许改：

给 MIMO 明确通用 API 签名、返回类型和最小示例。例如 drawer API：

```python
level = "middle"  # only "top", "middle", or "bottom"
handle_pos, hook_quat, pull_dir = get_cabinet_drawer_handle_pose(level)
progress = get_cabinet_drawer_progress(level)
open_fraction = float(progress.get("open_fraction", 0.0))
hooks = get_drawer_sleeve_hook_poses(level)
```

这是允许的，因为它不是答案，而是 API 使用规范。没有这个规范时，MIMO 会把 tuple 当 dict，或者把 region name 传给 drawer API。

不允许改：

- 在 prompt 中写“libero_goal/00 的真实 handle 坐标是 `[x, y, z]`，直接用它完成任务”。
- 把某次成功轨迹中的完整代码贴给模型。

### 3.3 Skill-level/action contract 优化

允许改：

对某类阶段加入通用动作约束。例如 drawer sleeve/hook 阶段：

```python
hooks = get_drawer_sleeve_hook_poses(level)
open_gripper()
goto_finger_midpoint_checked(hooks["prehook_finger_position"], hooks["hook_quaternion_wxyz"])
goto_finger_midpoint_checked(hooks["mouth_finger_position"], hooks["hook_quaternion_wxyz"])

for cand in hooks["sleeve_candidates"][:3]:
    goto_finger_midpoint_checked(cand["finger_midpoint_position"], cand["quaternion_wxyz"])
    align_open = measure_drawer_hook_alignment(level)
    if not (
        align_open.get("ready_to_close")
        or align_open.get("loose_hook_geometry")
        or align_open.get("centered_between_fingers")
    ):
        continue
    close_gripper()
    align_closed = measure_drawer_hook_alignment(level)
    contacts = measure_drawer_gripper_contacts(level)
```

这类规则的作用是限制“阶段动作应该怎么被验证”，而不是直接替 MIMO 完成任务。

对 drawer `test_progress` 阶段的通用约束也属于允许优化：

```python
alignment = measure_drawer_hook_alignment(level)
contacts = measure_drawer_gripper_contacts(level)
engaged = (
    alignment.get("closed_on_handle")
    or alignment.get("likely_hooked")
    or contacts.get("has_handle_contact")
)
if not engaged:
    print("STAGE_STATUS ... handle_engaged=False ...")
else:
    before = get_cabinet_drawer_progress(level)
    move_along_direction(pull_dir, 0.02_to_0.03, hook_quat)
    after = get_cabinet_drawer_progress(level)
```

这里统一了 sleeve/hook 与 test_progress 对“把手已接合”的判定：`closed_on_handle`、`likely_hooked`、`has_handle_contact` 任一为真即可进入短距离测试拉动。测试拉动只允许约 2-3cm，避免一开始就把把手带丢。

不允许改：

- 写一个 `_drawer_fast_path_code()` 直接替 MIMO 完成 drawer stage，并计入正式评测。
- 把某个任务的成功 candidate index、stroke 数、固定坐标写死。

### 3.4 Failure feedback template 优化

允许改：

使用固定模板从原始 evidence 中抽取数值并生成反馈，例如：

```json
{
  "feedback_policy": "generic_stage_family_template_v0.1",
  "raw_evidence": "before=0.015, after=0.006, bddl_open=False...",
  "raw_repair": "...",
  "repair": "Stage verifier returned status=needs_repair... re-measure drawer progress."
}
```

这类反馈必须由代码自动生成，并保留原始信息。

不允许改：

- 人工看图后给某一帧写一句定制 feedback。
- 为某个 task 单独修改失败解释。
- 删除或覆盖原始 `raw_evidence/raw_repair`。

## 4. 什么只能用于调试，不能计入主评测

下面这些可以用于 smoke test、素材验证、debug，但不能计入 MIMO+KITE 主评测：

### 4.1 Deterministic fast-path

代码位置：

- `capx/envs/stage_trial.py`
- 开关：`use_deterministic_stage_fast_paths`

含义：

runner 不问 MIMO 生成代码，而是直接使用我们预先写好的固定模板，例如：

- `_drawer_fast_path_code`
- `_pick_lift_fast_path_code`
- `_transport_fast_path_code`
- `_release_fast_path_code`

用途：

- 验证阶段边界是否合理。
- 验证失败帧是否能保存。
- 准备方法图素材。

正式评测：

必须关闭。

```yaml
use_deterministic_stage_fast_paths: false
```

### 4.2 任务级人工修补

不允许：

- 为 `libero_goal/03` 单独写一段“打开 top drawer 然后放 bowl”的代码。
- 根据某一次成功轨迹复制坐标。
- 针对单个 task 调阈值，而不是按 task family 调通用阈值。

### 4.3 事后人工筛选成功代码

不允许：

- 从 historical success code 里找一段成功代码塞给 MIMO。
- 失败后由人工写 repair code 再继续跑，并计入成功率。

允许：

- 保存 historical success reference 做离线分析。
- 在报告中说明某类 API/动作模式常失败，然后把它抽象成通用 contract。

## 5. 当前 case 的结论

任务：

```text
libero_goal/00: open the middle drawer of the cabinet
```

### 5.1 fast-path smoke test

输出目录：

```text
outputs/test_online_stage_kite_generic_feedback_goal00_20260626_225544
```

结果：

- 成功。
- 产生 3 个在线失败帧。
- 但所有 stage 都命中 deterministic fast-path。

结论：

这只能证明在线失败帧采集和反馈包生成是通的，不能作为 MIMO+KITE 主评测结果。

### 5.2 no-fast-path 初始测试

输出目录：

```text
outputs/test_online_stage_kite_nofastpath_goal00_20260626_230553
```

结果：

- 失败。
- 卡在 `middle_drawer_ground_handle`。
- MIMO 主要错误是 API contract 不清楚：
  - 把 `get_cabinet_drawer_handle_pose(level)` 返回值当 dict。
  - 传入 `wooden_cabinet_1_middle_region` 而不是 `"middle"`。
  - 调用参数数量错误。

结论：

失败不是因为缺少任务答案，而是通用 API 使用规范缺失。因此允许加入 API contract block。

### 5.3 no-fast-path + API contract 测试

输出目录：

```text
outputs/test_online_stage_kite_nofastpath_apicontract_goal00_20260626_232600
```

结果：

- 失败。
- 但 `middle_drawer_ground_handle` 已经通过。
- 后续进入 `middle_drawer_sleeve_or_hook_handle`。
- 第 2 次之后的 LLM 调用已经带失败帧图像输入。
- 当前卡点变成真实动作策略：没有稳定套住/夹住把手。

结论：

API contract 优化有效，把失败从“API 不会用”推进到“动作策略不稳定”。下一步应该加入 drawer sleeve/hook 的通用 action contract，而不是恢复 deterministic fast-path。

## 6. 后续优化流程

每次优化都应该按下面流程走：

1. **定位失败类型**
   从 `stage_trace.json`、`online_stage_feedback.json`、`all_responses.json` 里判断失败属于：
   - API contract 错误
   - stage boundary 不清楚
   - verification 缺失
   - action strategy 不稳定
   - model query/network error
   - physical execution failure

2. **判断是否允许优化**
   问两个问题：
   - 这个改动是否适用于一类阶段或一类任务？
   - 这个改动是否仍然让 MIMO 生成当前 stage CAP？

   如果答案都是是，可以进入方法优化。

3. **只改通用模板**
   优先改：
   - stage prompt contract
   - API signature/return contract
   - action contract
   - verifier rule
   - feedback template
   - preflight checker

   不改：
   - 单任务坐标
   - 单任务成功代码
   - 单轨迹 hard-coded repair

4. **跑同一个 case 验证局部改善**
   比较优化前后：
   - 卡在哪个 stage
   - 是否进入更后面的 stage
   - 是否减少 API/preflight/runtime 错误
   - 失败帧是否进入后续 LLM prompt

5. **再跑 LIBERO40**
   只有当单 case 证明通用优化确实改变失败类型，才进入 40 task 评测。

## 7. 评测报告必须记录的字段

每次正式评测至少记录：

- `output_dir`
- `model`
- `use_deterministic_stage_fast_paths`
- `use_online_stage_kite_feedback`
- `max_total_stage_attempts`
- `max_total_stage_attempts` 必须不超过 `10`
- `round_timeout_sec`
- `task_success_count`
- `successful_trial_count`
- 每个失败任务的 first failed stage
- 每个失败任务是否有 online feedback image input
- API/preflight/runtime 错误统计
- failure stage family 统计

报告中必须明确：

```text
fast-path on 的结果只用于调试，不计入主结果。
fast-path off 的结果才是 MIMO + Stage-CAP + Online-KITE 的主评测。
```

## 8. 一句话总结

我们的优化边界是：

```text
允许把 Codex 探索得到的经验固化成通用阶段边界、API contract、动作 contract、验证器和失败反馈模板；
不允许把 Codex 或人工找到的单任务成功代码、坐标、轨迹作为隐藏 oracle 注入评测。
```
